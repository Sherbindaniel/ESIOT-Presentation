1. Introduction and learning objectives

An Interrupt Service Routine (ISR) is a special function or handler executed by a processor in response to an interrupt event. The event temporarily redirects normal program execution so the processor can acknowledge or service the event, then usually resumes the interrupted context.

Examples include a timer reaching its period, a UART receiving a byte, a GPIO edge, an ADC conversion completing, or a network controller reporting a packet.

Core idea: Interrupts let a processor react to events without continuously polling every device. The ISR should normally do the minimum urgent work and defer longer processing to the main loop, task, or thread.

Learning objectives

  • Distinguish an interrupt, interrupt request, ISR, and polling.
  • Trace interrupt entry, context preservation, handler execution, and return.
  • Understand priority, latency, nesting, masking, and pending flags.
  • Write ISR-safe embedded code and avoid race conditions.
  • Analyze timing and debug common interrupt failures.

Prerequisites & terminology

  • CPU context: register values and program state needed to resume execution.
  • Interrupt request (IRQ): signal or event asking for processor attention.
  • Vector table: mapping from interrupt sources to handler entry addresses.
  • Latency: time from event/request to the start of the ISR.
  • Priority: relative urgency used to arbitrate competing interrupts.
  • Masking: temporarily disabling or blocking selected interrupt requests.
  • Pending flag: records that an event needs service.
  • ISR-safe shared data: data accessed by both an ISR and foreground/task code with appropriate synchronization.

3. Working principle: step by step

  1. Event occurs. A peripheral detects a condition, such as a UART receive register becoming full.
  2. Request is raised. Hardware sets a request or pending flag. The request may remain pending if masked.
  3. CPU checks eligibility. Global enable state, per-source enable, priority, and current execution state determine whether it can be accepted.
  4. Current context is preserved. The CPU and/or compiler saves the program counter, status register, and any required registers. The exact mechanism is architecture-specific.
  5. Handler is selected. The vector table or interrupt dispatch mechanism identifies the correct ISR.
  6. ISR services the source. It acknowledges the interrupt as required, captures time-sensitive data, and records work to be done later.
  7. Return from interrupt. A special return instruction or runtime mechanism restores the interrupted context; execution resumes unless another eligible interrupt is serviced first.
Important: An interrupt request is not the same as an ISR. The request is the event/condition; the ISR is the code executed to handle it.

Common ISR types

  • External/hardware: GPIO edge, timer, UART, ADC, SPI, DMA completion.
  • Processor exceptions: faults, illegal instructions, memory protection violations; handling rules differ from ordinary IRQs.
  • Maskable: can be disabled or masked under defined conditions.
  • Non-maskable: designed for critical events and not blocked by ordinary interrupt masks.
  • Nested: a higher-priority interrupt can preempt a lower-priority handler if the architecture and configuration allow it.

4. Timing, latency, and priority

Illustrative timing view. It is not a measured waveform and does not represent a particular MCU.

Total response time ≈ interrupt latency + time to reach the required action inside the ISR

For a system with interrupt latency \(L\), ISR execution time \(C\), and event deadline \(D\), a basic requirement is that the time to the required action be within the deadline. In a simple non-nested model, a rough check is \(L+C \le D\). Real-time analysis may also need blocking, higher-priority interference, critical sections, and scheduling delays.

What affects latency?

  • Time spent with interrupts masked.
  • Higher-priority handlers already running or pending.
  • Instruction completion rules and CPU architecture.
  • Context stacking, vector dispatch, flash/cache wait states, and bus contention.
  • RTOS critical sections and peripheral synchronization.
Engineering distinction: Short ISR execution time and low interrupt latency are related but different. Latency is the wait before service begins; execution time is how long the handler runs.

5. Embedded-C example

Generic illustrative pattern: a timer ISR sets a flag, while the main loop performs the longer work. Register names and interrupt declaration syntax vary by MCU, compiler, and framework.

#include <stdint.h>

/* Shared between ISR and foreground code.
   volatile prevents certain compiler optimizations; it is not a lock. */
static volatile uint8_t tick_pending = 0;

/* Replace this declaration with the MCU/compiler's correct ISR syntax. */
void TIMER_IRQHandler(void)
{
    /* Acknowledge/clear the timer interrupt source as required
       by the specific MCU reference manual. */
    tick_pending = 1;  /* Keep the ISR short. */
}

int main(void)
{
    /* Configure timer, clear pending state, enable its interrupt,
       then enable global interrupts according to the MCU manual. */
    while (1) {
        if (tick_pending) {
            /* If multiple ticks must be counted, use a counter or queue
               with a suitable atomicity/overflow strategy instead. */
            tick_pending = 0;
            perform_periodic_work();
        }
        /* Other foreground work */
    }
}
Portability note: This is a pattern, not a drop-in program: perform_periodic_work() and the hardware-specific acknowledgement/configuration must be supplied. The flag pattern can lose event counts if repeated interrupts occur before the flag is consumed. Use an atomic counter, queue, or RTOS primitive if every event matters.

Why keep an ISR short?

  • Reduces blocking time for other interrupts.
  • Improves predictability and helps meet deadlines.
  • Limits risk of stack exhaustion and timing jitter.
  • Prevents long operations from delaying the foreground application.

6. Safe ISR design and debugging

Recommended practices

  • Acknowledge the interrupt source correctly to prevent repeated entry.
  • Capture time-critical data immediately, then defer parsing, logging, and calculations.
  • Keep shared data access atomic or protect it with a suitable synchronization strategy.
  • Use volatile for memory-mapped registers and certain asynchronously changed variables, but do not mistake it for atomicity or mutual exclusion.
  • Avoid blocking calls, sleeps, unbounded loops, and ordinary mutexes inside an ISR unless the platform explicitly supports a specific ISR-safe API.
  • Use a queue, ring buffer, event flag, or RTOS “give from ISR” API where appropriate.
  • Check stack usage, nesting depth, interrupt priority, and worst-case execution time.
  • Read the exact MCU reference manual: flag-clearing semantics differ across peripherals.

7. Worked timing examples

Example 1 — Basic interrupt response

Given: latency = 4 μs, ISR execution time = 7 μs. Find approximate time from event to ISR completion, ignoring interference.

T ≈ L + C = 4 μs + 7 μs = 11 μs

Answer: approximately 11 μs. This estimate assumes no additional blocking, nesting, or deferred action.

Example 2 — Deadline check

Given: a control event must be serviced within 25 μs; worst-case latency is 6 μs and time to the required action is 8 μs. Is the deadline met?

Response to action = 6 μs + 8 μs = 14 μs

Answer: yes, under the stated assumptions, with 11 μs of margin. The full ISR need not finish before the deadline if the required action occurs earlier.

Example 3 — Event rate and service budget

Given: an interrupt arrives every 500 μs and the ISR takes 20 μs. Find the fraction of CPU time consumed by this ISR, assuming no other overhead.

Utilization = C / T = 20 / 500 = 0.04 = 4%

Answer: about 4% of CPU time. At higher rates, include entry/exit overhead, queue processing, and other interrupt workloads.

9. Core electronics / embedded interview questions

Expand each question to review a concise interview-ready answer.

1. What is an ISR?
A handler executed when an enabled interrupt or exception is accepted. It services the event and normally returns to the interrupted context.
2. How is an interrupt different from polling?
Polling checks a condition repeatedly; interrupts notify the CPU asynchronously. Interrupts can reduce wasted checking but introduce concurrency and timing complexity.
3. Why should an ISR be short?
Long handlers increase blocking and latency for other work, raise jitter, and can threaten real-time deadlines. Capture urgent data and defer heavy processing.
4. What is interrupt latency?
The delay from the interrupt event/request to the beginning of service, influenced by masking, priority, current execution, and hardware/software entry overhead.
5. What is a vector table?
A table or mapping that identifies reset, exception, and interrupt handler entry points. Exact layout is architecture-specific.
6. Does volatile make a variable thread-safe?
No. It constrains certain compiler optimizations but does not ensure atomicity or mutual exclusion. Use suitable atomic operations, critical sections, or synchronization primitives.
7. What causes an ISR to execute continuously?
Often the source is not acknowledged/cleared, the interrupt condition remains asserted, or the wrong flag-clearing sequence is used. Consult the peripheral reference manual.
8. Can an ISR call printf() or allocate memory?
Usually avoid it. Such calls may block, use locks, take unpredictable time, or be non-reentrant. Record compact data and print/process it later in foreground code.
9. What is nested interrupt handling?
A higher-priority interrupt preempts a currently executing handler when permitted by the architecture and configuration. Nesting raises stack and worst-case timing concerns.
10. How would you measure ISR execution time?
Toggle a GPIO at ISR entry and exit and measure it with an oscilloscope or logic analyzer; alternatively use a cycle counter or trace facility. Account for instrumentation overhead.
11. A UART receives bytes faster than the main loop consumes them. What would you do?
Read the receive register promptly in the ISR, place bytes in a bounded ring buffer, signal foreground processing, and size the buffer from peak rate and maximum service delay. Detect and handle overflow.
12. How do you safely share a multi-byte counter between ISR and main code?
Check whether the target can access it atomically. If not, briefly mask the relevant interrupt around a copy, use a supported atomic type/operation, or use a platform-provided synchronization approach. Keep critical sections short.

Industry perspective

ISRs are fundamental in motor-control loops, sensor acquisition, UART/SPI communication, power converters, automotive ECUs, medical instruments, industrial controllers, and RTOS-based products. Engineers validate both correctness and worst-case timing, not merely whether the handler runs in a demonstration.

11. Quick revision sheet

High-priority facts

  • ISR = code; interrupt request = event/condition.
  • Typical flow: event → request/pending → eligibility/arbitration → context save → vector/handler → service/acknowledge → return.
  • Latency is time before service starts; execution time is time spent in the handler.
  • Priorities, masking, and nesting influence response time.
  • Keep the handler short; defer heavy work.
  • volatile is not a synchronization primitive.
  • Always verify interrupt flag semantics in the exact MCU reference manual.
